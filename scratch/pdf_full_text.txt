1. Overview & Scope
This document covers Route 1 — the Sales Order Masters that sit underneath the Order Creation module:
Customer, Color, Article, Size (Series + Size), and Accessories (including the Thread sub-system and the two
new Thread support masters). It is organised the same way as the Raw Material Procurement module
document: every master has its own complete Data Structure table first, listing every field explicitly, followed
immediately by that master's own Functional Points. Edge cases and validations are covered section by
section afterwards, and the rules that apply across the whole portal — view mode, section-wise editing, audit
history, column filters, and global search — are collected once in a Global Points section at the end, in the
same structure and formatting already used for Route 2, since they apply here unchanged.
In scope:
• Customer, Color, Article, and Size (Series + Size) masters
• Accessories Master, covering Buttons, Lace, Tassel, Dori, Elastic, Beads & Sequins, and Thread
• The Thread sub-system: base thread fields plus the six Thread Patterns (Kantha, Couching, Stitching,
Embroidery, Button Tacking, Handwork)
• Two new masters: Thread Sizes (packaging/units, with the procurement suggestion engine) and Thread
Brand & Color Code
• Visual interface mockups for the Dori and Thread (Kantha/Couching) consumption flows
Out of scope for this document:
• The Order Creation Module's own workflow — this remains exactly as shown in the recorded
demonstration video; only the master data feeding it is documented here (see Section 9).
• Raw Material Procurement (Route 2) — documented separately.

11. Global Points — Apply Across the Whole Portal
These rules are not specific to any one master above — they are the standing behaviour for every screen and
every record in this portal, already established for Route 2 and carried over here unchanged, in the same
structure and formatting.
11.1 Global Search Bar
A static global search bar sits at the top-right corner of the portal at all times, for platform-wide searching
across records — customers, colors, articles, sizes, accessories, and threads alike.
11.2 View Mode by Default, with Section-wise Edit
• Once any record is saved, it always opens in a read-only View Mode by default — never straight into an
editable form.
• A saved record's View screen is split into logical sections, each with its own independent Edit button, so
one section can be unlocked and changed without disturbing the rest of the record.
• Alongside the section-level controls, the complete page still offers an overall Save and Edit, for when the
whole record is being handled at once.
11.3 Column-wise Filters on Every Table
On top of the header of every table listing saved records — customers, colors, articles, sizes, and accessories
— each column has its own filter/search control, so users can narrow the list by any column, not only by the
global search bar.
11.4 Activity History & Audit Trail
Every transactional module maintains a detailed Activity History (Master modules are optional, but
recommended here given how frequently these masters are edited). Whenever a record is created, edited,
updated, approved, rejected, deleted, or restored, the system captures the complete activity automatically,
recording:
• Date and time of the activity
• User name and role
• Type of activity (Create, Edit, Update, Delete, Approval, Rejection, Restore, etc.)
• Module name, and record name/number
• Field(s) modified, previous value, and updated value
• Remarks (if applicable)
• IP address / device information (optional, for future implementation)
History is shown in an easy-to-read timeline / activity-log format on each record, so any user can immediately
see who did what, to which field, from what value to what value, and when.

11.5 Field-Level Editability & Section-wise Saving
• Each major section of a record carries its own Save, Edit, Cancel, and Delete controls, so one section can
be saved while others are still being worked on.
• Every master supports full Create, View, Edit, Delete, and Activate/Deactivate.
• Every master provides a “Create New” option wherever it is referenced from a transaction screen, so a
new master record can be created without leaving the page in progress; new records become available in
the relevant lookup lists immediately, with no page refresh needed.
11.6 Interface Standards
• Every screen should be attractive, professional, interactive, responsive, properly aligned, and easy to
understand and operate — a modern ERP look, not a traditional data-entry form.
• Number fields carry no spinner arrows and start blank with a placeholder example, never a default 0.
• Free-text fields auto-capitalise the first letter of each word as the user types.
12. Validations, Edge Cases & Challenges
Covered section by section, in the same order as the masters above.
12.1 Customer, Color, Article, Size
• A Customer's GSTIN, if entered, must pass format validation before save.
• A Color's Hex Code must be a valid 6-character hex value regardless of whether it was picked visually or
typed/searched.
• Deleting or deactivating an Article, Color, or Size already used on an existing Sales Order must not remove
or break that historical reference — it should simply stop appearing in new-record selections.
• An Article's Sort Order change must immediately reflect in both the card/tile display and the Order Detail
Form without requiring a rebuild of the article list.
• Reordering Size Series via drag-and-drop must persist immediately and reflect in every screen that lists
series in order (not just the master screen itself).
12.2 Accessories — General
• Switching Accessory Category after some fields are already filled in must not silently carry over values
that don't apply to the new category (e.g. Tassel Type fields left behind after switching to Lace).
• The four common fields (Maximum Buffer, HSN Code, Description, Active Status) must behave identically
across every category — any category-specific logic should never touch these.

12.3 Dori, Elastic, Beads & Sequins
• Removing a width from the multi-select after its consumption box already has a value must remove that
box (and its value) cleanly, without leaving an orphaned field or silently keeping the value against a width
that's no longer selected.
• Selecting a single width should not generate a box — per the rule, boxes only auto-generate once two or
more widths are selected; the single-width case still needs its own consumption entry point (via the same
Step 3 area) so a Dori entry with only one width is not left without a way to record consumption.
• Each “Add More Fabric” block (Fabric Quality → Width(s) → Consumption) must be independently
editable and deletable without disturbing other fabric blocks already saved against the same
Dori/Elastic/Beads accessory.
12.4 Thread — Base & Patterns
• Changing the Thread Pattern after some pattern-specific fields are filled in must not carry incompatible
data across (e.g. Thread Per Piece from Stitching should not silently populate Thread Per Stitch if the
user switches to Kantha).
• Selecting “Other” on any internal (non-master-driven) dropdown must unlock its manual text field, and that
typed value must save and display correctly wherever the dropdown's value is shown elsewhere.
• Kantha and Couching must be built from one shared configuration definition, not duplicated separately,
so a fix or change to one does not have to be manually repeated in the other.
• The one-time Global Thread Stitching Metric is entered once and applies to both Kantha and Couching —
it must not be asked for again per Article Block.
• An Article → Placement → Thread Line block, once added, must be independently editable and
removable without disturbing other Article blocks under the same accessory.
• Stitching's Thread Per Piece auto-populates the BOM Quantity per Piece, but a manual edit to that BOM
value afterwards must not be silently overwritten if Thread Per Piece is changed again later — the two
need a clear rule for which one wins.

12.5 New Thread Masters
• The Procurement Suggestion Engine must account for partial-box and partial-cone scenarios (e.g. a
requirement that doesn't divide evenly into whole boxes or cones) and present the closest sensible
combinations rather than only exact matches.
• A Thread Size record's Packaging Type of “Other” must still work correctly inside the suggestion engine —
a custom packaging type should not be silently excluded from suggested combinations.
• A Color Code entered manually (not via the picker) must still generate the same colored-square preview
as one chosen visually — the preview cannot depend on which entry method was used.
13. Deferred / Out of Scope

• Manufacturing Defaults for thread Placements — referenced here as a source for some placement values,
